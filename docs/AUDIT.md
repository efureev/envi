# v1: известные дефекты и точка отсчёта

Справочный документ. Полный аудит `v1.3.1` проводился 2026-08-12 по ревизии `181e1b1`; здесь
оставлено только то, что не потеряло силу: почему `v1` нельзя использовать и с какими числами
сравниваются числа `v2`.

Что было сделано по итогам — в [CHANGELOG.md](../CHANGELOG.md).
Что осталось сделать — в [UPGRADE-SPEC.md](UPGRADE-SPEC.md).

## Статус v1

`v1` заморожен и снят с основной ветки: код `v2` занял корень репозитория. По тегам `v1` доступен
по-прежнему — `go get github.com/efureev/envi@v1.3.1` работает и продолжит работать, — но исправлений
не получит.

**Дефекты ниже в `v1` не исправлены и исправлены не будут.** Все они закрыты в `v2` регрессионными
тестами, названными по идентификатору находки (`regression_test.go`).

## Дефекты v1

Все воспроизведены запуском через публичный API, а не выведены из чтения кода. Ссылки на строки —
по ревизии `181e1b1`.

| # | Место | Суть |
|---|---|---|
| **C1** | `envi.go:352` | `Merge` паникует на любом ключе верхнего уровня, отсутствующем в приёмнике: в `addRow` уходит заведомо `nil` |
| **C2** | `envi.go:419` | `RemoveRow` паникует, если блока с префиксом ключа нет: результат `GetBlock` не проверяется на `nil` |
| **C3** | `row.go:197` | `mergeRowMap` ищет по сырому ключу, а пишет по нормализованному. При multi-file `Load` с расхождением регистра строка заменяется целиком — комментарии и тени теряются молча |
| **C4** | `block.go:91` | `AddPrefixedRows` молча выбрасывает строку с чужим префиксом |
| **H1** | `envi.go:267` | `Get` возвращает `nil` для существующей корневой строки, если есть блок с тем же префиксом: нет провала в скан корня |
| **H2** | `row.go:99` | `Merge` затирает значение пустым |
| **H3** | `envi.go:35,179,514` | Порядок исходного файла не сохраняется: `Parse` и `Load` всегда сортируют |
| **H4** | `row.go:153-174` | Round-trip не байт-идентичен: значения переписываются кавычками |
| **H5** | `row.go:10-12`, `block.go:7-12`, `envi.go:17` | Семь параметров поведения живут в глобалках пакета. Конкурентный `Marshal` при живом `SetIndent` — гонка данных, подтверждённая детектором |

Следствие H5, важное для понимания, почему `v1` не чинился точечно: набор его тестов
порядково-зависим, `go test -shuffle` красный, и включить шафл в CI было нельзя.

Проверить всё это можно только на теге:

```shell
git worktree add /tmp/envi-v1 v1.3.1 && cd /tmp/envi-v1
go test -shuffle=1          # красный: порядковая зависимость
```

Характеризационные тесты, фиксировавшие каждый дефект, жили в корне до переезда `v2`; они снялись
вместе с `v1` и в истории git остались на коммите перед ним.

## Baseline производительности

Числа зафиксированы навсегда: `v1` из репозитория снят, перемерить их можно только на теге.
Именно от них заданы бюджеты `v2`.

Документ `.env` сгенерирован реалистично: строки сгруппированы в блоки по 10, каждая третья с
комментарием, каждый блок с заголовком. Go 1.26.5, darwin/arm64, Apple M5 Pro, `benchstat`,
`-count 8`.

| Бенчмарк | sec/op | allocs/op | Пропускная способность |
|---|---:|---:|---:|
| `Parse/1000` | 11.27 ms | 295 687 | 2.81 МиБ/с |
| `Marshal/1000` | 568.9 µs | 10 914 | — |
| `Get/1000` | 1.362 µs | 35 | — |
| `NewRow` | 831.0 ns | 19 | — |

Причина деградации локализована и измерена: `regexp.MustCompile` вызывался на каждой разбираемой
строке (`parse.go:58,79,87`) и на каждый `normalizeKey` (`row.go:141`). Одна компиляция шаблона
строки стоила 5.469 µs и 146 аллокаций — то есть половину всех аллокаций разбора создавал один
вызов. Ручной однопроходный разбор той же строки стоит 4.5 ns и ноль аллокаций.

**Это и есть причина, по которой парсер `v2` написан руками.** Вынос регулярок в переменные пакета
дал бы 23×, отказ от них — три порядка. Если однажды возникнет желание «упростить» сканер обратно
на `regexp`, начинать нужно с воспроизведения этих замеров.
