## 1. Открытые пункты

### 1.1 Покрытие ядра ниже заявленного порога

Порог в исходном ТЗ — **≥ 90%**. Фактически: ядро **86.9%**, `bind` 92.6%.

Непокрытое сосредоточено в опознаваемых местах, а не размазано:

| Область | Что не покрыто |
|---|---|
| Блоки больше 8 строк | `buildIndex`, ветка `find` через карту, `noteAppended` при живом индексе — то есть **весь путь хеш-индекса**. Все тестовые блоки мельче порога |
| `Block` | `clone`, `Prefix`, `Rows`, `sortRows` |
| Разное | `ParseBytes`, `QuoteStyle.String`, `Order.String`, `WithBlockComment`, `Row.SetInlineComment` |
| Пути ошибок | `Save` (ошибки записи, `Sync`, `Rename`), `truncate` в `SyntaxError` при длинной исходной строке |

Самое ценное здесь — первая строка: порог `blockIndexThreshold = 8` введён в фазе 4 ради экономии
аллокаций, и переключение на хеш-индекс сейчас **не проверяется ни одним тестом**. Начинать нужно
с блока на 20+ строк.

### 1.2 Метрика «масштабирование `Get` ± 10%» непригодна

Величина лежит ниже уровня шума: два прогона на одной машине дали +21% и +6.5% при неизменном коде.
На 26 нс разброс между запусками сопоставим с самим эффектом.

Заменить формулировку на проверяемую: **число аллокаций `Get` равно нулю независимо от размера
документа** — это и есть доказательство O(1), оно детерминировано и уже выполняется.

### 1.3 Остаток обвязки

Из пунктов T6 исходного аудита не сделаны два: **CodeQL** и **шаблоны issue**. Ни то, ни другое не
блокирует релиз.

### 1.4 Последствие переезда в корень

`v1` снят с ветки, `v2` занял корень. Побочный эффект: **бюджеты производительности больше не
перепроверяются автоматически** — сравнивать не с чем, числа `v1` в [AUDIT.md](AUDIT.md) стали
константами.

Если понадобится сравнение заново, `v1` достаётся из тега:

```shell
git worktree add /tmp/envi-v1 v1.3.1
```

Чего это не отменяет: регресс `v2` относительно самого себя ловится обычным `make bench` и
`benchstat` между двумя прогонами. Именно так и надо проверять изменения в сканере.

## 2. Известные ограничения v2

Это описанное и протестированное поведение, а не дефекты. Каждое можно снять, но каждое чего-то
стоит.

| Ограничение | Причина | Чего будет стоить снятие |
|---|---|---|
| Одинаковый префикс, встречающийся в файле **не подряд**, при `Env.Add` сливается в первый блок — порядок меняется | `Add` для блоков намеренно сливает, чтобы ручная сборка документа вела себя предсказуемо. Парсер обходит это через `appendBlock` | Разделить публичный контракт: `Add` сливает, новый `Append` — нет |
| Документ, объявляющий ключ **дважды**, не воспроизводится построчно: строки схлопываются | Модель хранит один `Row` на ключ; вторая строка становится тенью | Хранить дубликаты как отдельные элементы — заметное усложнение индекса |
| **Смешанные** окончания строк нормализуются к первому встреченному | Терминатор запоминается один на документ | Хранить терминатор на строку |
| В теге `bind` опция `default=` обязана быть последней | Значение по умолчанию может содержать запятую, и разделить их иначе нельзя | Ввести экранирование в теге |

## 3. Пути развития

Порядок — по убыванию отдачи на вложенный труд.

### 3.1 Подстановка переменных `${VAR}`

Автор `v1` это задумывал: в `parse.go:12-13` лежит закомментированный `variablePattern`, а в
`parseLine` — закомментированный вызов подстановки. До реализации дело не дошло.

```dotenv
ROOT=/srv/app
LOGS=${ROOT}/logs
```

Вопросы, которые нужно решить до кода: подстановка на чтении или на запросе значения (второе лучше
дружит с round-trip — в файле остаётся `${ROOT}`); что делать с неизвестной переменной; брать ли
значения из окружения процесса. Естественное место — опция `WithExpand(...)` у декодера плюс
`Env.Expand(key)`.

### 3.2 `bind`: свои конвертеры и валидация

Сейчас набор типов закрыт. Две очевидные точки роста:

- реестр конвертеров: `bind.WithConverter[T](func(string) (T, error))` для типов, не реализующих
  `encoding.TextUnmarshaler`;
- проверка после заполнения — тег `validate:"..."` или интерфейс `Validate() error` на структуре,
  с включением в тот же агрегат ошибок, что уже собирает `bind.Error`.

### 3.3 Потоковая обработка очень больших файлов

Сейчас документ материализуется целиком. Для сценария «прочитать, поменять один ключ, записать» на
файле в сотни мегабайт это лишнее. `Decoder` уже потоковый на входе; не хватает варианта, который
отдаёт строки по одной и не строит `Env`:

```go
for row, err := range dec.Rows() { ... }   // iter.Seq2
```

### 3.4 Diff двух документов

`Env.Diff(other) iter.Seq[Change]` — что добавилось, изменилось, исчезло. Полезно и само по себе,
и для тестов, и для проверки `.env.example` на соответствие рабочему `.env` в CI.

### 3.5 Утилита командной строки

`envi fmt` (привести файл к каноническому виду), `envi diff a b`, `envi check .env .env.example`.
Ложится на существующий API целиком, отдельного пакета не требует — только `cmd/envi`.

## 4. Как проверять, что ничего не сломалось

```shell
make check         # fmt, vet, lint, тесты -race -shuffle=on
make fuzz          # фаззинг парсера и round-trip по 30 с
make bench         # сравнивать через benchstat с прошлым прогоном
```

`-shuffle=on` не опция: он и есть доказательство, что в пакете нет порядково-зависимого состояния.

Бюджеты производительности, достигнутые в фазе 4 (Go 1.26.5, darwin/arm64, Apple M5 Pro,
`benchstat`, `-count 8`) — их нельзя ухудшать без явного решения:

| Метрика | v1 | v2 |
|---|---:|---:|
| `Parse/1000` | 11.27 ms | **237 µs** (134 МиБ/с) |
| `Parse/1000`, аллокаций | 295 687 | **4 405** |
| `Marshal/1000` | 568.9 µs | **22.6 µs** |
| `Marshal/1000`, аллокаций | 10 914 | **5** |
| `Get/1000` | 1.362 µs | **27.8 нс**, 0 аллокаций |
| `bind.Decode`, 50 полей | — | **1.0 µs**, 2 аллокации |

Отдельное требование, выполненное и подлежащее сохранению: **`regexp` в модуле нет вовсе.**
